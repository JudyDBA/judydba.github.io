AI 에이전트가 일할 수 있는 시스템인가 — 5가지 점검

2026-10-19

에이전트를 붙였는데 "생각보다 못한다"는 말을 자주 듣는다. 그런데 들여다보면 모델이 모자란 경우보다, 에이전트가 볼 수도 만질 수도 잴 수도 없는 시스템인 경우가 더 많다.

최근 읽은 글 하나가 이걸 잘 정리했다. 게임 개발자 Kyle Kukshtel의 「게임 개발용 AI 하네스를 설계하는 방법」이다(원문, GeekNews 요약). 게임은 코드 밖의 상태·데이터·화면이 많아서 에이전트에게 특히 불투명한데, 그 블랙박스를 여는 방법을 다룬다. 읽다 보니 게임만의 이야기가 아니었다. 일반 서비스와 사내 시스템에도 그대로 옮겨진다.

아래는 그 글의 원칙을 일반 시스템용 점검 항목 다섯 개로 바꾼 것이다.

1. 같은 상태를 다시 만들 수 있는가 (재현성)

에이전트가 무언가를 고쳤다면, "고치기 전과 같은 조건"에서 다시 돌려봐야 효과를 안다. 그런데 테스트 데이터가 매번 다르고, 난수·시간·외부 응답에 따라 결과가 바뀌면 에이전트는 변경을 검증하는 대신 상태를 맞추는 데 시간을 쓴다.

  • 시드 고정, 고정된 테스트 데이터셋, 외부 API 응답 녹화(스텁)가 있는가
  • 버그를 "재현 절차 문서"가 아니라 명령 한 줄로 재현할 수 있는가

2. 작업이 명령이나 API로 정리돼 있는가 (명령화)

원문에서 가장 좋았던 대목은 명령 패턴이다. 상태를 바꾸는 모든 요청을 직렬화 가능한 명령 객체로 만들면, 기록을 재생해서 버그를 재현하고, 사람이든 AI든 텍스트로 명령을 써서 재빌드 없이 시스템을 조작할 수 있다.

  • 관리자 화면에서만 가능한 작업이 있는가 (에이전트에겐 벽이다)
  • 주요 작업이 CLI·API·스크립트로 노출돼 있는가
  • 작업 기록(감사 로그)을 그대로 다시 실행할 수 있는가

3. 설정과 데이터가 코드 밖에 있는가 (설정 분리)

값 하나 바꾸는 데 코드 수정과 배포가 필요하면, 에이전트의 반복 주기는 배포 주기에 묶인다. 원문은 게임 수치를 외부 데이터로 빼서 비개발자 7명이 새 빌드 없이 실험하게 한 사례를 든다. 에이전트도 그 "팀원" 중 하나가 될 수 있다.

  • 임계값·문구·가격·규칙이 하드코딩돼 있지 않은가
  • 바꾼 값을 되돌리기 쉬운가 (버전 관리되는가)

4. 화면 없이 돌릴 수 있는가 (헤드리스)

원문 댓글에서 인상 깊었던 말이 있다. 가장 가치 있었던 요청은 "내가 PC를 쓸 수 있게 화면 없이 실행하는 방법을 찾아줘"였고, 그게 되자 여러 인스턴스를 병렬로 돌릴 수 있게 됐다는 것이다.

  • 핵심 로직을 UI·브라우저 없이 실행할 수 있는가
  • 동시에 여러 벌을 띄워도 서로 간섭하지 않는가

5. 결과를 숫자로 평가할 수 있는가 (수치 평가)

"좋아졌나요?"를 사람이 눈으로 판단해야 하면 루프가 멈춘다. 원문은 스크린샷을 그대로 주지 말고 이미지 차이를 수치로 비교하라고 하고(odiff의 "85% 유사" 같은 값), 프로파일러 결과도 그래프 대신 텍스트 원시 데이터로 주라고 한다(samply).

  • 성공/실패를 판정하는 테스트·지표가 있는가
  • 결과가 사람용 대시보드에만 있지 않고 기계가 읽는 형식(CSV·JSON·로그)으로도 나오는가

직접 해본 것: 출처 검사 한 줄이 바꾼 것

나도 매일 아침 뉴스 브리프를 만드는 에이전트를 돌린다. 한동안 "출처 링크가 내용과 안 맞는다"는 문제가 반복됐다. 프롬프트를 아무리 다듬어도 줄지 않았는데, 5번(수치 평가) 을 넣자 달라졌다. 모든 출처가 전체 URL인지, 실제로 열리는지, 지난 브리프와 겹치지 않는지를 검사하는 스크립트를 두고, 실패하면 에이전트가 고치거나 항목을 지우게 했다. 그 뒤 두 번 연속 실행에서 출처 19개, 18개 중 실패는 0건이었다. 이 이야기는 다음 글에서 자세히 쓴다.

그래서, 어디서부터?

다섯 개를 한 번에 갖출 필요는 없다. 원문 저자도 아주 작은 프로젝트에서는 이런 장치를 거의 쓰지 않았다고 했다. 규모가 커질수록 필요성이 커진다.

순서는 보통 이렇게 권한다.

  1. 5번 수치 평가부터. 판정 기준이 없으면 나머지를 갖춰도 에이전트가 "됐다"고 말할 근거가 없다.
  2. 그다음 1번 재현성. 같은 조건에서 다시 돌릴 수 있어야 비교가 된다.
  3. 반복 작업이 많다면 2번 명령화와 3번 설정 분리.
  4. 병렬이 필요해지면 4번 헤드리스.

15문항 셀프 진단

내 시스템이 어디쯤인지 궁금하다면, 위 다섯 영역을 15문항으로 만든 셀프 진단을 써보시라. 3분이면 끝나고, 영역별 점수와 가장 약한 곳, 먼저 손댈 일을 보여준다. 입력한 내용은 브라우저 밖으로 나가지 않는다.
